**Виявлена вразливість XSS**

У браузерному клієнті SecureLab виявлено використання `innerHTML` для відображення недовірених даних `Incident.Description` та `IncidentComment.Text`.

Основний потік даних: введення Description → збереження в PostgreSQL → JSON-відповідь API → відображення через DOM.

Причиною вразливості була інтерпретація тексту користувача як HTML. У локальному навчальному сценарії це підтверджено нешкідливим marker, який змінював лише атрибут тестового DOM-елемента.

**Виправлення**

У файлі `src/SecureLab.Api/Client/browser-lab.js` небезпечні операції `innerHTML` замінено спільною функцією `renderSafeText()`, що використовує текстові вузли DOM через `replaceChildren()` і `document.createTextNode()`.

Значення в базі даних та JSON-відповідях API не змінювалися. Виправлення виконано на рівні відображення.

**Повторна перевірка**

Після виправлення:

- Marker відображається як звичайний текст.
- `childElementCount = 0` для перевіреного Description.
- `markerResult = null`.
- Текст коментаря не створює HTML-елементів.
- Апострофи, лапки, символи `<`, `>`, Unicode та HTML-подібні рядки відображаються правильно.
- Перевірено опис довжиною 3900 символів.
- Для Morgan підтверджено доступ до дозволеного інциденту; для Bob — відмову в доступі до чужого.

**Залишковий ризик:** інші неперевірені DOM-контексти та сторонні JavaScript-компоненти потребують окремого аналізу.

### 2.2. CSP та заголовки безпеки

У `Program.cs` реалізовано CSP у режимі enforcement.

Використано такі директиви:

- `default-src 'self'`
- `script-src 'self'`
- `style-src 'self'`
- `connect-src 'self'`
- `img-src 'self' data:`
- `frame-ancestors 'none'`

Перевірено заголовок `Content-Security-Policy` у відповіді сервера зі статусом `200 OK`.

Контрольована спроба завантажити зображення з `http://localhost:4173/x.png` була заблокована директивою `img-src`.

Основний клієнт та навчальні сторінки продовжують працювати. Для Development-довідника `/scalar` передбачено окремий виняток, який не послаблює CSP основного клієнта.

Додатково перевірено:

**X-Content-Type-Options: nosniff** — обмежує небажане визначення MIME-типів браузером.

**Referrer-Policy: no-referrer** — запобігає передаванню адреси попередньої сторінки. Для перевіреного клієнта така політика відповідає потребам навігації.

**frame-ancestors 'none'** — забороняє вбудовування сторінок у фрейми та зменшує ризик clickjacking.

### 2.3. Аналіз XSS, CORS, CSRF та authorization

**XSS** пов'язаний із небезпечною інтерпретацією недовірених даних браузером. У SecureLab причину усунено через безпечне формування DOM.

**CORS** визначає, чи може JavaScript одного origin прочитати відповідь сервера іншого origin. CORS не замінює серверних механізмів доступу.

**CSRF** пов'язаний із можливістю надсилання браузером запитів із cookie користувача без належної перевірки наміру. Для операцій зі зміною стану необхідний окремий antiforgery-захист, який розглядатиметься в ЛР №6.

**Authorization** забезпечується сервером незалежно від CORS. Права доступу перевіряються для кожного захищеного ресурсу.

## 3. Відповіді на контрольні питання

**1. Чому значення з бази даних може залишатися недовіреним?**

Тому що воно могло надійти від користувача або іншого недовіреного джерела. Збереження в БД не робить текст безпечним для HTML-контексту.

**2. Що таке source, transformation і sink?**

Source — джерело даних; transformation — їх обробка або передавання; sink — операція, під час якої дані використовуються, зокрема відображаються в DOM.

**3. Чим відрізняються stored, reflected та DOM-based XSS?**

Stored XSS використовує збережені недовірені дані. Reflected XSS пов'язаний із відображенням даних із поточного запиту. DOM-based XSS виникає через небезпечні операції JavaScript із DOM.

**4. Чому блокування `<script>` не усуває XSS?**

Тому що HTML має й інші механізми виконання JavaScript. Правильне рішення — безпечне виведення даних відповідно до їхнього контексту.

**5. Коли використовують textContent, а коли sanitizer?**

Для звичайного тексту використовують `textContent` або текстові вузли. Sanitizer потрібний лише за обґрунтованої необхідності підтримувати обмежений HTML.

**6. Чому sanitizer не слід реалізовувати регулярним виразом?**

Регулярні вирази не забезпечують надійного аналізу всіх особливостей HTML і браузерного парсингу.

**7. Із яких компонентів складається origin?**

Із протоколу (scheme), імені хоста (host) та порту (port).

**8. Що містить CORS preflight і хто його ініціює?**

Браузер автоматично надсилає OPTIONS із заголовками Origin, Access-Control-Request-Method і, за потреби, Access-Control-Request-Headers.

**9. Хто визначає CORS-політику і хто її застосовує?**

Сервер оголошує дозволи через HTTP-заголовки, а браузер застосовує їх до доступу JavaScript.

**10. Чому curl може читати відповідь, коли браузер показує CORS error?**

Тому що `curl` не застосовує браузерну same-origin policy.

**11. Чому CORS не замінює authorization та CSRF-захист?**

CORS не перевіряє права користувача і не забезпечує повноцінного захисту операцій зі зміною стану від CSRF.

**12. Чому wildcard origin не поєднується з credentials?**

Для credentialed CORS-відповідей потрібний конкретний дозволений origin, а не `*`.

**13. Чому CSP не замінює safe DOM rendering?**

CSP може заблокувати виконання небезпечного коду, але сама по собі не усуває небезпечну операцію `innerHTML`.

**14. Які ризики зменшують nosniff, Referrer-Policy та frame-ancestors?**

`nosniff` обмежує MIME sniffing, `Referrer-Policy` — передавання інформації про адресу сторінки, а `frame-ancestors` — небажане вбудовування та clickjacking.
