## Мета і правила доступу

У локальному ASP.NET Core SecureLab API було відтворено та виправлено IDOR/BOLA для ресурсу `Incident`, реалізовано серверний контроль ролей і володіння ресурсом, обмежено видимість списку та дочірніх коментарів. Reporter читає й редагує свої інциденти; Analyst читає інциденти та виконує окремо дозволений перехід `New → Triaged`; Administrator не отримує необмежених повноважень. Для всіх ролей DELETE заборонено.

Застосована політика відмов: `401` — анонімний запит, `403` — існуючий ресурс поза правами суб'єкта, `404` — відсутній ресурс, `400` — некоректне дозволене поле, `409` — конфлікт даних або переходу. Для звичайного PUT обрано A-08a: сторонні `OwnerUserId`, `Role`, `Severity`, `Status` ігноруються, DTO містить лише `Title`, `Description`.

## Основний finding: до → причина → виправлення → після

**Контекст.** Ресурс `Incident`, головна змінювальна дія `PUT /api/incidents/{id}`; Alice з роллю Reporter та інцидент Bob з іншим OwnerUserId. Використано тільки синтетичні навчальні ресурси.

**Гіпотеза.** Якщо endpoint перевіряє тільки автентифікацію й знаходить Incident за клієнтським `id`, Alice зможе змінити ресурс Bob.

**До.** Вразливий стан повернув `204 No Content` на PUT Alice → Bob; наступне читання підтвердило зміну Title чужого інциденту. У Git-історії локального проєкту збережено vulnerable commit (hash зазначено вище; підлягає звірянню).

**Причина.** Відсутність необхідної перевірки authorization для комбінації `subject + action + resource + context`, зокрема ownership перед мутацією. Успішний login не дорівнює дозволу на чужу дію.

**Виправлення.** Централізовано `IncidentAccess.Allows(...)`; список обмежено за OwnerUserId для Reporter; PUT змінює лише дозволені поля; DELETE заборонено; Child IncidentComment перевіряється через батьківський Incident; `triage` потребує Analyst та статусу New.

**Після.** Той самий за змістом запит Alice → Bob отримав `403`; стан ресурсу не змінився. Дозволене редагування власного ресурсу Alice й читання Analyst продовжили працювати. Відмова Reporter у triage — `403`, дозволений triage Morgan — `204`, повторний triage — `409`.

**Залишковий ризик.** Політика `403` розкриває факт існування чужого ресурсу (прийнятий навчальний компроміс). Додаткове scoping маршрутів `search` і `severity-summary` (A-11) належить до рівня «Відмінно» та не заявляється виконаним. Cookie-authenticated mutation потребують окремого CSRF-посилення в наступних лабораторних; конкурентні переходи не охоплено.

**Схема рішення:** запит з route id → перевірена cookie й `ClaimsPrincipal` → завантаження `Incident` → `IncidentAccess` за роллю, owner та дією → перевірка стану / DTO → статус відповіді → безпечний audit для denied privileged action.

## Додаткові результати

- Автентифікація через Identity cookie; OwnerUserId нового Incident береться лише з перевіреного principal.
- Перевірка власника для редагування, `403` і відсутність змін чужого ресурсу.
- Delete відхиляється навіть для власного ресурсу, після відмови запис збережений.
- Reporter не отримує `IsInternal` у details; Analyst читає internal-коментар після перевірки батьківського Incident.
- `authorization.denied` фіксує subject, action, resource, UTC time, result, traceId; не фіксує password, token, cookie чи повний request body.
- Автоматичні перевірки виконувалися через xUnit, `SecureLabApiFactory`, `CookieClient.LoginAsync` і `WebApplicationFactory<Program>`.
- Підсумкова команда `dotnet test .\tests\SecureLab.Api.Tests\SecureLab.Api.Tests.csproj --configuration Release` завершилася **35 succeeded, 0 failed**.
